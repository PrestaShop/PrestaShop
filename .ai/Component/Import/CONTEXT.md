# Import Component

## Purpose

Multi-phase, batch-capable import engine for the BO **Advanced Parameters > Import** page: file upload/normalization, column-to-field mapping, per-entity importers driven by a phase model (validate → insert/update → associate → finalize), and a server-side `ImportJob` aggregate tracking progress across HTTP requests. Does not handle localization pack imports (`LocalizationPackImporter` is separate).

**Under active refactoring** (#41907). The target architecture below is the source of truth for the ongoing PR series; [PLAN.md](PLAN.md) tracks the roadmap, per-field decisions, and progress. Anything marked *deprecated* must not be built upon.

## Non-obvious patterns

- **The "migrated" pre-#41907 system was never switched on.** Step-1 submit forwards to the legacy controller; the Symfony step-2 controller, `Core\Import\Importer` and both `Adapter\Import\Handler\*` classes are unreachable code. They are line-by-line legacy ports (ObjectModel, validation entangled with insertion) — deprecated, never extend them.
- **Phase model.** Each entity importer declares an ordered subset of phases: `validation`, `database`, `association`, `finalization` are the common conventions. Self-referencing data (product accessories, category parents) is resolved in `association`, *after* every row has been inserted — so row order in the file never matters, including A↔B mutual references. `finalization` covers whole-dataset work (category ntree rebuild). Phase definitions (technical id + translatable label) live **in code only**; the DB stores phase-id strings. Phase ids are open strings — importers may declare custom phases: `ProductImporter` runs `validation` → `database` → `association_validation` (custom, pausing pre-check of the accessories targets) → `association`.
- **Single run with pausing phases.** A phase may be declared *pausing* (validation is): when it completes having produced at least one WARNING or ERROR, the job stops with status `awaiting_confirmation`; a clean pausing phase continues in the same job without pause — no click needed for a clean file. **Notices never pause** (the empty-row notice is the only one today, and a stray blank line must not cost a confirmation click). Calling `ContinueImportJob` on an `awaiting_confirmation` job implicitly accepts the messages and resumes — there is no separate confirm command, so a polling client cannot deadlock a paused job; `CancelImportJob` is the reject path. `options.dryRun` truncates the phase list after the phase whose id is `validation` (API validate-only; the BO does not use it) — and because `getPhases()` takes no context, an importer validating under another id cannot offer a dry run (decision 47).
- **One state shape.** `ContinueImportJob` returns the same `ImportJobState` DTO as the `GetImportJobState` query — polling and state reads share one structure, so a client never needs a second call per tick. Progress is measured in PHASES, each weighing the same, with the current one contributing its fraction: a phase's unit count does not exist until the phase is entered, so units of one phase can never weigh against another's.
- **Store-and-skip invalid rows.** Validation scans the whole file; invalid row indexes are stored (one sparse cumulative set) and later phases skip them; the import finishes even with errors. An internal sanity cap (10 000 invalid rows) fails the job instead ("file malformed" — wrong separator/encoding). All persisted state is bounded by constants (caps), never by file size — no per-row table.
- **Association existence is checked twice, both times phase-based.** (1) The pausing `association_validation` phase between `database` and `association`: every file row exists in the DB by then, so each batch probes accessory targets with plain per-row DB lookups — stateless, cursor-resumable, no in-memory identity set, and it shares the target-decision logic (`ProductFinder::findTarget()`) with the association phase so both always agree. (2) At `association` phase resolution, defensively (DB may have changed) — failures are errors but the run completes.
- **Existence-failure severity is per-field policy owned by the importer**: some references auto-create (product categories, manufacturers, features — legacy behavior kept), others warn-and-drop (suppliers — an address is required to create one; accessories).
- **Required values are validated PER ROW, create-aware — never per mapped column.** A value is only mandatory when the row creates the entity, and one file can create and update, so the row validator asks the finder whether the row resolved to an existing entity first (`ProductRowValidator` demands a name only when `findRowMatch()` came back empty). `EntityField::isRequired`/`getRequiredFields` are deprecated: they only ever fed mapping-screen hints, and requiring a column would reject legitimate update-only files (`match_ref` + `reference` + `price`). Legacy never enforced them server-side either.
- **Writes must never destroy what the file does not describe.** Several CQRS commands replace whole collections rather than merging (`SetSuppliersCommand` deletes the suppliers missing from its list; `UpdateProductSuppliersCommand` overwrites the reference and price of the association it is handed; `UpdateProductTypeCommand` deletes combinations or pack contents when the type changes). An importer must therefore read the current state and merge, dispatch only on a real change, and warn at validation when a conversion is destructive — an import file is a partial description of an entity, not its full state.
- **Ambiguity severity follows the blast radius.** None of the columns the import resolves by (`manufacturer.name`, `supplier.name`, `shop.name`, `feature_lang.name`, `feature_value_lang.value`, sibling `category_lang.name`, `product.reference`) has a DB unique constraint, so every lookup returns ALL matching ids ordered by id ASC (legacy used `Db::getValue()` with no `ORDER BY`, i.e. non-deterministically). An ambiguous **link** (manufacturer, supplier, shop, feature, feature value, category path, accessory owner and target) is a WARNING carrying the match count, and the lowest id is used; an ambiguous **identity** — a `match_ref` reference matching several in-scope products — is a row ERROR, because updating an arbitrary one of them is destructive. The error is raised in the pausing `validation` phase and defended in the database phase by an explicit check in the row importer. **The lookup services are split by the create/no-create seam**: match-only finders (`Engine\EntityImporter\Finder\` — product identity/targets, supplier, shop) and resolve-or-create resolvers (`Engine\EntityImporter\Resolver\` — manufacturer, category path, feature) both return pure data through exactly two result types (`FoundEntity` — with `matchedBy` stored per match, so one result can mix strategies — and `ResolvedEntity`), never build messages and never throw — severity and wording are owned by the calling importer. Caching is shared: `PositiveLookupCacheTrait` memoizes id-list lookups for both families and caches **only non-empty results** (the import creates entities mid-run, so a cached miss could go stale — a cached hit never can), and `QuietResolutionTrait` adds the resolve-or-create template whose stripped `ResolvedEntity` makes creation/ambiguity surface **once per batch request**, not once per row and not once per run (the caches live for the service lifetime). `EntityFinderInterface`/`EntityResolverInterface` pin the single-value shapes; product identity, category paths and feature values keep richer signatures outside them.
- **Soft-deleted rows count as absent.** `ImportEntityExistenceChecker::SOFT_DELETE_TABLES` (`tax_rules_group`, `shop`) adds `deleted = 0` to the probe, and the shop name lookup does the same: assigning a historized entity would resurrect it. Only tables an importer actually probes are listed.
- **Re-import is an update, not a failure.** Where a command rejects a duplicate (`AddSpecificPriceCommand` → `NOT_UNIQUE_PER_PRODUCT`, `AddVirtualProductFileCommand` → `ALREADY_HAS_A_FILE`), the importer looks the existing record up first and dispatches the Edit/Update command instead. This matters beyond the field itself: those throws land in the row catch-all, so the row would be marked errored and its accessories dropped by the association phase.
- **Local file paths are confined to the CONTENT directories** (`admin/import`, `upload/`, `img/`, `download/`, system temp) — deliberately not the whole shop root, which also holds `app/config/parameters.php` and `.env`. A fetched file can become a downloadable virtual product file, so this is a security boundary, not a convenience check. The directories are **injected via DI** (`FileDownloader` ctor, wired in `import_engine.yml` with `!php/const` / `%prestashop.admin_dir%`) — the engine class never reads the legacy constants itself.
- **Batching resumes by row position + opaque reader cursor.** At `StartImportJob` the file is normalized once (encoding → UTF-8, Excel → CSV, BOM stripped) into a job-scoped working file that always uses one canonical CSV dialect (`;`, `"` — constants on `CsvImportFileNormalizer`): the user-chosen separator AND the configured skip rows are consumed at normalization — the engine reader is dialect-free and the working file holds data records only (row indexes = 0-based data-record indexes; presenters add the skip count back for source-file line numbers). The engine tracks progress in row positions; after each batch the reader returns an opaque resume cursor persisted on the job (the CSV reader's cursor is a byte offset for `fseek` — no O(n²) re-scan; other formats define their own), which the engine never interprets. One batch budget may span a phase boundary; per-phase unit counts are computed ONCE at phase entry (`countPhaseUnits()` → stored on the context by `enterPhase()`, 0 units → phase skipped) and default to the working file's record count, which the normalization pass itself measured (`ImportJobContext::getDataRecordCount()`) — importers never read the file to count; completion = last phase's offset reaching its total. A job resumed in a LATER request is replayed with `ImportJobContext::restoreProgress()` (phase, total, offset, cursor, skipped rows) rather than by entering the phase and applying a synthetic batch result: `enterPhase()` rewinds offset and cursor, which is right on first entry and wrong on resume. The resumable reader is a standalone interface yielding plain `array<int, string>` records (the legacy `DataRow` layer is deprecated). Importers extend `AbstractEntityImporter` (batch loop, phase guard, default unit count) — implementing the interface directly stays supported.
- **Engine classes are deliberately NOT final and use protected members** (deviation from the project-wide final-by-default rule): modules must be able to extend or decorate the importers and their internals.
- **Multishop: the job's `ShopConstraint` is the single scope reference, and the ONLY shape shop scope travels in.** `ImportJobContext` carries it frozen; configuration reads go through `ShopConfigurationInterface` with the explicit constraint; the `match_ref` reference lookup is scoped to the constraint's shops and a reference existing only OUTSIDE the scope fails the row (never a duplicate product); auto-created entities are associated to the constraint's shops. Name lookups (feature/manufacturer/supplier/shop) stay deliberately GLOBAL so a job scoped to another shop reuses the entity instead of duplicating it (they return every match — see the ambiguity bullet above; the finder/resolver services carrying them are described there too) — and reusing a feature ENSURES its `feature_shop` association covers the job's shops. The context exposes NO shop id: code needing concrete ids resolves the constraint through `ShopListResolverInterface` (`resolveShopIds()` to fan out, `resolveRepresentativeShopId()` for a deterministic single shop), like the shop context subscribers and the grid query builders. A plain `int $shopId` parameter in new engine code is a defect unless the method is a genuine single-shop leaf. Three paths are arithmetically single-shop and stay so until the multishop pass: the stock delta (read one shop's quantity, apply one delta), forced-id creation and `AddProductCommand` (both write into ONE shop then associate from it). `StartImportJob` is where a scope wider than one shop is refused, so those paths fail once and legibly instead of once per row.
- **Hybrid persistence, no ObjectModel.** Importers dispatch existing CQRS commands for everything commands cover; a narrow import-specific repository handles the two gaps (forced-ID creation for the *force IDs* option, `date_add`). This keeps importers in `Core`. The batch sequencer dispatching commands through the bus is a sanctioned composition service — it does not violate the "handlers never call handlers" rule (nothing injects another handler).
- **Registry by service tag.** Importers are tagged services collected into `EntityImporterRegistry`: one source of truth for the BO entity dropdown, the mapping page's field list, and batch dispatch. The tag is applied automatically to every **autoconfigured** service implementing `EntityImporterInterface` (`registerForAutoconfiguration` in `PrestaShopExtension` — a class-level attribute is not needed and `#[AutoconfigureTag]` on the interface is ignored by Symfony 6.4). Modules register importers the same way: an autoconfigured service definition is enough (see the `demoentityimporter` example module).
- **Product row steps by service tag.** The product row import is a list of tagged `ProductRowStepInterface` steps collected by `ProductRowImporter` (`core.import.product_row_step`, autoconfigured on the interface like the importer tag above), one per concern, ordered by explicit priorities in `import_engine.yml` where some orderings are load-bearing. Modules add a step the same way: an autoconfigured service definition is enough (no explicit priority means priority 0, i.e. after every core step). The interface is an extension point WITHOUT the ADR-0017 promise and may evolve in a minor version (decision 25).
- **Bounded messages, merged across batches by the Adapter.** Messages are structured (`severity, phase, rows, field, message`) and accumulated by `ImportJobMessageLedger`, which lives in the Adapter rather than the engine: its job is merging what the database holds with what the engine just produced. Engine `ImportMessage` in, domain `ImportJobMessage` out, keyed on `ImportMessage::coalesceKey()` and never on a re-derived key, so the in-batch and cross-batch merges always agree. Two caps bound a column decoded on every request: 100 rows sampled per message while `rowCount` keeps counting the true total, and 1 000 distinct messages per severity with what the cap discards counted in `droppedMessages`. Reporting works identically for a 100-row and a 5M-row file.

- **The sequencer owns the loop, and slices it.** `ImportJobSequencer` enters phases, spends the caller's unit budget on the importer and persists what happened. The budget is spent across several importer calls rather than one: slicing (`MAX_UNITS_PER_STEP`) bounds what an interruption costs — at most one slice of rows written after a cancellation is observed, at most one slice of progress lost to a fatal — without shrinking the batch the caller asked for. Handlers stay thin: lock, check, delegate, report.

- **Cancellation is arbitrated by the database, not by a transaction** (none exist yet, #42385). Every status change is a compare-and-set — `ImportJobRepository::transitionStatus()`, one `UPDATE … WHERE status IN (…)` read back afterwards — that a concurrent Cancel wins by getting there first; the ORM cannot write `status` at all (`updatable=false`), so a progress write never carries it; and the status is re-read between slices (`readStatus()`, a scalar query bypassing the identity map — `$job->getStatus()` would only repeat what this request loaded) and asked again right before truncating. A request that loses adopts what the row holds: a slice that raced a cancellation still persists its progress under CANCELLED, since the rows it wrote are real and the merchant has to be able to tell what went in. The per-job flock only serializes Continue-vs-Continue and decides who deletes the working file — and is taken BEFORE the status probe, or a Cancel squeezing in between would have removed the file the batch is about to read. The flock directory is `var/cache/locks/import`, the root `CacheClearLocker` uses, because `cache:clear` wipes `kernel.cache_dir` and would hand a second Continue a fresh inode.

- **Where a value lives.** A **column** for identity, scope, indexed fields, anything written by every batch, or a scalar the report shows — progress in columns keeps every slice's UPDATE small, since a JSON blob would be rewritten whole. **`context`** (JSON) holds exactly the frozen inputs `ImportJobContext` is rebuilt from; **`options`** (JSON) holds what the job does and is the only half modules may extend, so a module key can never shadow the reader configuration. The entity carries its OWN status enum (`PrestaShopBundle\Entity\ImportJobStatus`) and the adapter converts: persistence must not depend on the CQRS layer, which is also why the repository returns `?ImportJob` and takes strings rather than value objects.
- **Cleanup.** A `finished` job clears its skipped-row list and its resume cursor (the COUNT survives, so the report can still state it); a `cancelled` or `failed` one keeps them — bounded data, and what a later retry of the rest needs (#42424). Every terminal status deletes the working file and keeps the capped messages for the post-run report. Old jobs are garbage-collected two ways: an opportunistic purge inside `StartImportJob` and the `PurgeImportJobs` command behind `prestashop:import:purge-jobs`. The purge goes by `date_upd` alone, whatever the status: a closed tab leaves a job pending, paused or running, and `date_upd` moves on every slice, so a job that stopped moving for the retention was abandoned. Rows go first and files second, so a working file is judged an orphan against an already-pruned table — which also collects the file of a job whose row never existed; only files older than the retention are considered, since the Start handler writes the working file before persisting its row.
- **Source confinement is the handler's, and the temp roots are real.** The Admin API hands `StartImportJobCommand` `UploadedFile::getPathname()` verbatim (core `UploadedFileNormalizer`), with nothing before the handler that could move the file, so `StartImportJobHandler` accepts two kinds of root: the files the import directory lists — depth 0, no dotfile, no `index.php`, as `FileFinder` — which are ours and deleted after normalization unless `keepSourceFile`; and the temp directories PHP writes uploads to, `upload_tmp_dir` and the system temp (read only; under a web SAPI only an `is_uploaded_file()` of the current request, under the CLI unchecked). The client's file name travels separately as the optional `fileName`, which the API maps from the normalizer's `clientOriginalName`.
- **What a failure may quote.** Only an `ImportEngineException` or a PrestaShop `DomainException` has its message reach the report, for one row (`ProductRowImporter`) and for the whole job (`ImportJobSequencer`) alike; anything else is logged in full and replaced by a generic text — never `CoreException`, which wraps SQL text from the ObjectModel layer.
- **The reader is chosen by content.** `ImportFileFormatDetector` reads the first bytes — a ZIP or OLE2 signature means PhpSpreadsheet, anything else CSV with the merchant's separator — because an API upload has no extension and a client's extension is a claim, not a fact.
- **Reader abstraction.** CSV only today; the reader interface is deliberately narrow so a Symfony-Serializer-based reader (e.g. JSON with native multi-language fields) can be added without touching importers.
