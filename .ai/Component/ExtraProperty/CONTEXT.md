# ExtraProperty Component

## Purpose

Lets modules (or the BO registry page) add **typed extra fields** to existing entities (Product, Order, Customer…) without altering core tables. One registration provisions storage and surfaces the field in the FO (Smarty lazy arrays), the migrated BO (Symfony forms + grids) and the Admin API. Storage is **column-based** (one DB column per property), not EAV, so values are indexable and joinable. Example module: [`demoextraproperty`](https://github.com/PrestaShop/example-modules/tree/master/demoextraproperty).

## Storage

- **Registry `extra_property_definition`**: one row per property, unique `(entity_name, module_name, property_name)`; `module_name` NULL = core-owned. `constraints` holds the **constraint DSL string**. `table_name` freezes the physical table; `controller_name` is an override-only BO permission subject.
- **`nullable` and `enumValues` are not stored** — the live column is their source of truth (`SHOW COLUMNS` injects synthetic row keys at hydration, same for `multi_shop` and `primary_key_name`).
- **Value tables** created lazily per entity and scope: `common` → `{table}_extra`, `lang` → `{table}_extra_lang`, `shop` → `{table}_extra_shop`. Each **mirrors the primary key of its native base table** (`{table}`, `{table}_lang`, `{table}_shop`) by introspection, so every grid LEFT JOIN is 1:1 (no `GROUP BY`) and `contact_extra_lang` has no `id_shop` while `product_extra_lang` has one. `isMultiShop()` is schema-derived; reader, writer and grid use it so they never reference a missing `id_shop`. SHOP scope requires a native `{table}_shop` table (`orders`, `cart` cannot take it).
- Storage column = `{module}_{property}` (`{property}` for core fields); SQL type from `ColumnDefinitionMapper`. The table is dropped once only PK columns remain.

## Non-obvious patterns

- **Failure contract.** The registry throws `ExtraPropertyRegistryException` (reason = exception code, see the class). CQRS handlers wrap every core exception into the Domain `ExtraPropertyRegistrationFailureException::fromCoreException()`; the controller maps domain codes to flash messages. **`Module::registerExtraProperty()` / `unregisterExtraProperty()` do NOT throw**: they return `false` and push the message to `$this->_errors`; call the registry directly to get reason codes. Both inject the module name when unset.
- **Registry atomicity: DDL first, no transaction** (MySQL DDL auto-commits). `register()` runs the DDL before the row write and compensates by dropping a column it just added if the row write fails; `unregister()` deletes the row first, then drops the column.
- **Re-registration reconciles drift.** Non-destructive changes (default, size increase, nullable relax, enum addition, index) are applied via `ALTER … MODIFY`; destructive ones (type/scope change, size decrease, NULL→NOT NULL, enum removal, table change) are refused — `ExtraPropertyRegistry::hasStorageChanges()` is the only place enforcing it. Module uninstall cleanup is manual (`unregisterExtraProperty($definition, dropData: true)`).
- **Entity name vs table name.** `getEntityName()` is logical (`order`, `combination`), `getTableName()` physical (`orders`, `product_attribute`) — SQL must use the table. Entity name: tableize → `CANONICAL_ENTITY_NAMES` (before class resolution, so `ProductAttribute` cannot hijack combination). Table: explicit `tableName` → `CANONICAL_ENTITY_TABLES` → declaring ObjectModel `$definition['table']` → entity name. `withOverrides()` re-resolves table and PK when the entity changes. ObjectModel/FO match with `filterByTableName()`, everything else with `filterByEntity()`. Two entities resolving to the same table + column → `STORAGE_CONFLICT`. A `controllerName` change is not destructive, a `tableName` change is.
- **Identifier safety.** The VO constructor validates entity, property, table, PK and storage column as SQL identifiers (≤64 chars), so DDL code embeds them without re-validating. Anchored validator regexes use the `D` modifier: without it `$` accepts a trailing `\n`.
- **Placement DSL** parsed by `AssociationEntryParser`: `associatedForms` `"formId[:path[:before|after]]"`, `associatedGrids` `"gridId[:columnId[:before|after]]"`, `associatedApis` `"/uri/{template}[:GET,PATCH]"`. An entry without path/column → dedicated form section / before the grid `actions` column; a null/empty list → not shown at all. Form field name, grid column id, SELECT alias and API list key all share `getFieldName()` = `extra_{module}_{property}` (scope not included).
- **Rendering.** Form type = `formType` override, else `ExtraPropertyFormTypeMap` default per type; LANG wrapped in `TranslatableType`. Grid column is derived from the logical type (BOOL → `ToggleColumn`, DATE → `DateTimeColumn`, JSON skipped, else `DataColumn`). Grids with id-first pagination (order grid, #42536) keep the columns but render them empty.
- **Constraints cross CQRS/API boundaries as the DSL string**, parsed eagerly by the commands; the VO holds `Constraint` objects. `ExtraPropertyConstraintParser::parse()` never throws (reports rejections; hydration keeps valid siblings and logs); `ExtraPropertyConstraintRenderer::render()` round-trips and throws on loss — it is the only writer of the column. `required` only drives the HTML attribute and the OpenAPI `required` list; server-side requiredness needs an explicit `NotBlank`.
- **Type compatibility is always enforced**, even with zero constraints: `ExtraPropertyValidator::isValueCompatible()` backs registration (`INVALID_DEFAULT_VALUE`), every write, and BO forms via the always-attached `ExtraPropertyTypeCompatibility` constraint.
- **Default values.** Typed end to end; one stringification `ExtraPropertyValueCaster::castDefaultValueForDb()` (bool → `'1'/'0'`) shared by row, DDL and schema comparison. A row-less entity reads back the default on every surface; TEXT-backed types (HTML, JSON) have no DDL default, only the registry one. `defaultValue` is immutable after creation.
- **Value shape and typing.** Reader returns / writer accepts `[moduleKey => [property => value]]` (`'_core'` for core fields); LANG with `langId = null` → `[id_lang => value]`, with an int → scalar. `ExtraPropertyWriter::writeAll()` casts for every path. JSON is stored encoded and exposed decoded; the validator checks it as its encoded string.
- **`ExtraPropertiesBag`** is the lazy dirty-tracking resolver behind `ObjectModel::$extra_properties` and the FO lazy arrays (opt-in via `AbstractLazyArray::initExtraPropertiesBag()`). Callers pass `forFrontOffice`; FO reads only see `display_front = 1`. `Context::isFrontOfficeContext()` returns FO for anything that is not a BO/API controller or CLI — legacy webservice, crons and standalone scripts included. The key is `extra_properties` in PHP/Smarty, `extraProperties` only in Admin API JSON.
- **Cart** supports COMMON scope only (no `cart_lang`/`cart_shop`); `CartFilter` whitelists the key for JS `prestashop.cart`. Cart values die at checkout: modules copy them onto the order at `actionValidateOrder`.
- **ShopConstraint (value multistore).** Writes fan out to every usable shop in scope in one multi-row UPSERT; SHOP-scope broad writes only touch shops the entity is associated with in `{table}_shop`, explicitly named shops always get their row, LANG rows cover the full scope. Reads pin one representative shop (default shop when in scope, else lowest id) — same rule as the BO/API context listeners. Toggle writes the inverse of the representative value to every shop in scope. `isStrict` is ignored. `ObjectModel` follows `$id_shop_list`.
- **Definition-level shop association** (`extra_property_definition_shop`) is a different axis than `isMultiShop()`: it restricts where a definition EXISTS. No rows → core-owned = all shops, module-owned = the module's enabled shops (a module with no `module_shop` row at all counts as unrestricted, registration runs before `enable()`). `associatedShopIds` is tri-state on write: `null` leaves stored rows untouched (a module upgrade cannot clobber a BO restriction), `[]` clears, a list replaces. PHP rule (`ExtraPropertyDefinition::isAvailableForShops()`) and SQL rule (`ExtraPropertyDefinitionQueryBuilder::applyShopContextRestriction()`) must stay in lockstep — `ExtraPropertyDefinitionAvailabilityConsistencyTest` fails on drift. `ExtraPropertyDefinitionShopFilter` short-circuits when multistore is not used. Deliberately unfiltered: OpenAPI schema, translation extractor, API list collector.
- **Admin API** (Admin API kernel only). Targeting is by literal `uriTemplate` + method, no class→entity inference. Items get a nested `extraProperties` object (LANG keyed by locale, SHOP flattened for the context shop); list items get the value inline under `getFieldName()`, reused from the grid query when available. Writes are filtered to the operation's definitions; `ExtraPropertyCQRSApiValidator` merges violations into the resource's 422. Do NOT flag `combinationId` as `#[ApiProperty(identifier: true)]` on list resources with a `{productId}` variable (ReadListener 404s).
- **BO registry page manages core-owned definitions only.** Module-owned rows get a disabled `viewAction()` where the shop association is the single editable field, enforced by `UpdateExtraPropertyDefinitionHandler` (loads with `getDefinitionById()`, refuses any other override on a module-owned row). Delete handlers load through `getUnprotectedDefinitionById()` (not found / module-owned guards). Writes persist with `withOverrides()` + `registry->register()`. Entity, property, type, scope and default are immutable. Bulk delete repeats the single-delete guard and unregister call (handlers never call handlers) and aggregates per-item failures. The form is 5 `CardType` sub-forms, data nested by card.
- **Service wiring gotchas.** `common.yml` (FO+BO): repository, cached decorator, reader, writer, validator — the definition `WriterInterface` has no FO alias (`backend.yml` only). `catalog.yml` is Symfony-kernels only; `ApiEndpointCatalog` needs swagger so it is admin-kernel only (`app/config/admin/services.yml`, with `AssociationExistenceChecker` and `ExtraPropertyDefinitionAdvancedType`). Loggers are injected via `@logger`, not `LoggerInterface` (modules redefining the logger caused circular references). `CachedExtraPropertyDefinitionRepository` implements both read and write interfaces and invalidates on write; the registry itself is uncached.
- **Validator in the FO legacy container.** It has no Symfony `validator`, so `src/Adapter/Container/ValidatorBuilderExtension.php` builds one with `GracefulConstraintValidatorFactory`, which skips (and `error_log`s) validators whose deps are absent in FO (`DefaultLanguage`). A LANG value loaded with a `langId` is a scalar: only unwrapped `All` rules run. See [CONTAINERS.md](../../CONTAINERS.md).
